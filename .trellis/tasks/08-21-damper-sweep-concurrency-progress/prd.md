# 修复阻尼器批量扫描并发与进度

## Goal

让受控 Agent 的 `DAMPER_PARAMETER_SWEEP` 对实际可用并发度诚实执行和展示；进度卡仅展示一致、可识别的批次与案例进度。

## Confirmed Facts

- 用户截图对应 `OPENSEESPY_INPROC` 的 4 个阻尼器参数案例。请求合同可保存 `maxConcurrentCases=4`，但运行时在 `PlatformStore._generate_real_damper_parameter_sweep_artifacts` 将该求解器的有效 worker 数强制设为 1，理由是进程内 OpenSeesPy 的全局 domain 不能在线程间复用。
- 因此当前 "批量并发正向求解" 阶段名称与实际执行不一致；这不是队列阻塞或偶发退化。
- 进度聚合的 22% 与截图一致：`(已完成 0 + 进行中案例 90% / 100) / 4 = 22.5%`，取整后为 22%。主进度是批次进度，案例行才是单案例进度。
- `JobProgressSection` 先显示后端消息（已含“已完成 0/4”），又再次渲染完成计数，造成重复文案。
- 单案例进度由求解器内部 `case_id` 写入进度文件，未映射到参数扫描的业务 `caseId`，因此界面显示不可读的哈希式 ID。
- 并发执行时，当前实现故意不透传单案例进度目录，避免多个案例覆盖同一进度文件；届时只能显示完成计数。这是实现限制，而非前端轮询问题。

## Requirements

- R1：`OPENSEESPY_INPROC` 的实际并发策略必须与用户可见的工作流/计划一致，不得把串行执行表述为并发。
- R2：批次主进度、完成数和单案例进度必须各自有明确口径，且同一完成数只显示一次。
- R3：单案例进度必须显示冻结参数案例的业务 `caseId`，不能泄露内部求解器 ID。
- R4：若支持多案例并发，进度文件必须按业务案例隔离写入，汇总不丢失或覆盖任一活动案例。
- R5：保留 ANSYS 的许可证并发上限、失败重试和现有 Job 取消/超时语义。

## Acceptance Criteria

- [x] 对 4 个 OpenSeesPy 参数案例，界面和运行摘要显示的有效并发度与实际最大同时运行数一致。
- [x] 运行中能清晰区分批次完成率和案例进度，且不重复显示“已完成 X/Y 个算例”。
- [x] 每个进行中的案例显示业务 `caseId`；并发时多个活动案例的进度互不覆盖。
- [x] 新增回归测试覆盖 OpenSeesPy 并发策略、进度聚合、业务案例 ID 映射和重复文案。

## Constraints

- 不修改现有用户未提交的风荷载与能力目录改动。
- 不在此任务中解锁独立 `SOLVER_BATCH` 平台 API，亦不改变 ANSYS 许可证策略。

## Key Decision

- OpenSeesPy 参数扫描改为每案例独立子进程，最大并发数使用冻结的 `maxConcurrentCases`（并受案例总数限制）。不使用线程池，不在同一 Python 进程内复用 OpenSeesPy domain。
- 未显式指定时，`maxConcurrentCases` 默认值为 4；所有入口仍校验 1–8，并在运行时取案例数上限。
- ANSYS 保持现有线程池、许可证上限和许可证失败串行重试行为，不纳入本次执行策略变更。
